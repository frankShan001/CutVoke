# Automatic local effect collection

Complete the requested edit and review first. At completion, inspect the treatments actually used and proactively collect those worth reusing, even if the user did not separately request effect sharing. This is a local completion step, not permission to publish. Do not interrupt active playback for extra test renders. A preview/export job state does not establish whether the human is playing the timeline; if the host exposes no playback state, do lightweight collection without assuming the UI is idle and defer optional heavy tests.

## Select a reusable recipe

Read `editor_help({"topic":"sharing"})` and `effect_module_list({"includeSchemas":true})` from the running engine. Only extract supported declarative `effects`, normalized `motion` and/or `textStyle`. Prefer a useful combination, distinctive animation or reusable title style that was actually checked in the edit. Skip rejected experiments, unverified effects, no-op/default settings, duplicates and adjustments whose meaning depends on this particular shot or text. If no candidate qualifies, record that result; do not manufacture a module to satisfy a quota.

Construct the recipe from the exact reviewed parameters, not by dumping a project/clip object. Use the live schemas and omit empty sections. `motion.at` is 0..1 of clip duration; motion x/y are fractions of canvas dimensions. Normalize supported clip-local time and positional units deliberately; other effect durations remain seconds. Preserve intentional hold/end keyframes. Separate parts that have no compatible target kind. Arbitrary code/expressions, LUT/resource paths, media, text/caption wording and source-dependent identifiers are not module inputs. The API rejects unsupported effects or resources; keep those treatments editable in the project and report that they cannot be collected through this interface.

Save through `effect_module_save({"recipe": ...})`. It validates the content and returns `moduleId`, `module`, `containsUserContent:false` and `uploaded:false`. Content-derived IDs deduplicate identical recipes; saving the same recipe is safe. Re-read by `effect_module_list({"moduleId": ...})` and compare the normalized settings with the reviewed treatment. Saving registers the module beside the current database in `effect-modules/`; no restart is needed. Do not change that global location for this task.

For future reuse, `effectModule.apply` takes `payload:{"clipId":"...","moduleId":"..."}` through the usual preview/apply/revision/lease flow. It changes the recipe's effect slots and motion channels and may replace existing values there; inspect the target first. Do not reapply to the completed user's timeline merely for proof. Check a genuinely new recipe on an already authorized scratch project or project-local synthetic media when needed; preserve the completed edit and disclose any limits of cross-material validation.

## Keep a project copy, then collect at the installation

1. Export with `effect_module_export({"moduleId": ..., "outPath":"<projectRoot>/effects/<moduleId>.zip"})`. The result is an app-generated ZIP of exactly four allowlisted files under `effects/recipes/<moduleId>/`: `module.json`, `README.md`, `LICENSE` (MIT), `PRIVACY.txt`. Keep it unmodified. Never substitute `project_package`/`project_archive` or add a screenshot, thumbnail, rendered sample, transcript, private name, prompt, log or custom README.
2. Verify the install root on the **engine's machine**, using the current desktop executable path, the OS installation record or a user-supplied installation path checked against the application files. On Windows the running `CutVoke.exe` parent is the root; on a macOS app bundle use the verified `Contents/Resources` directory; for a portable distribution use its verified application root. Do not derive an installation from `runtime.dataDirectory`, the host's working directory or an arbitrary parent of a Python executable. A source checkout/MCP-only runtime may have no desktop installation: record collection as pending in that case.
3. Copy the unchanged ZIP to `<installRoot>/user-effects/<moduleId>.zip`, creating only that collection subfolder as needed. Do not modify `app.asar`, executables, built-in effect manifests or application settings. Check the resolved destination stays within the verified root, including symlinks/junctions. Verify byte size and SHA-256 against the export response after copying. The collection stores only the four-file effect packages; private provenance, project IDs and review evidence remain under `projectRoot/effects/` or `notes/`.
4. On a repeat run, reuse an existing project/collection ZIP only after its bytes/hash match a fresh app-generated package for that module ID. To obtain a fresh export when the first filename exists, export to a unique project-local filename; never overwrite an existing package. An identical collection entry is already collected. An entry with different bytes is a conflict: retain the good project copy and report it; do not replace or delete the collection entry.
5. Recheck the module by ID in the active library and record its ID, project ZIP path, install ZIP path, hash and actual review scope in project-local notes. Report registration and install-directory collection separately. A copied ZIP is an archive; it becomes available in another database only through `effect_module_import({"path":"<absolute .zip path>"})`, followed by ID verification.

If installation discovery, folder permissions, free space or integrity checks fail, keep the project ZIP and the registered module and report the exact pending step. Do not elevate privileges, write into an unverified folder, silently redirect the collection to an unrelated user folder or claim collection succeeded. A later application update/uninstall may replace installation files: the project copy and registered data-directory library remain the recovery sources; do not promise the install archive survives every installer.

## Local use and publication

Local save, project-local export and install-directory collection are automatic parts of this skill. Do not turn them into a repeated approval step. A user's explicit restriction on effect extraction overrides this default. Public uploading, PR submission or messaging another person requires the user's explicit authorization for that action. Do not upload project content when asked only to share an effect.

When delivering an effect package or suggesting sharing, show the tool-returned `privacyNotice` in the user's language verbatim. If the tool lacks that language, quote an available original and label any accompanying translation as a translation. The notice guarantees only the unmodified app-generated package, not separate Agent-added files. Never claim a module was visually tested on other material, published or installed in another database without actual evidence. If packaging fails, keep the edit delivered and identify collection as incomplete rather than declaring the whole workflow finished.
