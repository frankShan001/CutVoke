# 渲染结果复用与性能验证

预览和导出共用 `RenderService` 的渲染链。这里的优化保留原有分辨率、效果算法、透明度和编码质量，减少重复准备工作。

## 复用边界

- 媒体信息：按规范化绝对路径、文件大小、修改时间、创建/变更时间和文件标识缓存；最多保留 256 项。同一素材的并发探测共用一次 ffprobe 调用，调用方拿到独立的结果字典。
- 帧时钟：按素材版本、源区间、帧率和 ffprobe 后端缓存；最多保留 256 项。预览裁剪、GPU 效果和栅格蒙版准备共享检查结果，均使用绝对区间结束时间。变速和不规则时间戳仍保留原有回退路径。
- 静态图形：仅复用原来已经允许折叠的静态蒙版或静态图形效果栈。键包含素材版本、实际滤镜图和 FFmpeg 后端；预览缩放进入滤镜图，所以草稿与原尺寸结果分开保存。图层位置等后续合成参数变化可复用上游像素。

静态像素以无损 RGBA PNG 字节保存在内存中，每个 `RenderService` 最多 128 项、64 MiB 压缩数据。超过单项容量的结果正常渲染但不驻留。元数据和像素分别使用 LRU 淘汰，避免缓存满后全部清空。

缓存合并同一键的在途计算，昂贵工作在锁外执行；不同键可以并行。失败结果不保存，后续请求可以重试。临时媒体仍属于各自请求，结束后删除；缓存不持有这些路径，也不修改工程 JSON。缓存随服务实例释放，不跨进程持久保存。

没有相关栅格蒙版的请求直接跳过该准备阶段的整工程深拷贝。

## 视频解码和动态效果

所有编译图均可使用保守的源端 seek：同一输入的每个引用必须直接进入 trim/atrim，视频须与序列具有相同的整数帧率、零起始时间，且实际时间戳通过检查。共享音视频输入取最早裁剪起点，保留一秒解码预卷和原始剩余裁剪量。效果、拖尾、变速和关键帧仍从片段自身起点执行，不跳过效果历史。非零流起始时间、无法核验的 VFR、非直接裁剪引用等继续使用原路径。

WebM 的毫秒时间基可以将 30fps 表示成 33/34ms 交替步长。验证使用整段帧格点相对于容器时间基的量化误差，拒绝累计漂移、丢帧和过粗的时间基，避免把正常录屏误判成 VFR。

不超过八秒的指定区间导出，在既有安全效果白名单允许时复用预览的有界视频求值；转场、未知时序效果等保留回退路径。视频时钟前移时，导出音频仍使用原图的片段与处理起点，避免分次裁剪导致混音或 AAC 输入变化。长导出继续使用既有分窗策略。

光编织与光学场可复用完整的无损 FFV1 中间媒体，单独限制为 32 项、64 MiB；单项超过 16 MiB 时直接保留磁盘路径，不读入内存。键包含效果参数、尺寸、帧率、片段时长、效果类型/版本、起始时间及前缀区间；合成位置改变可复用，效果或时间区间改变则重算。不能缓存的结果只供当前请求使用，并发请求各自保有临时文件。缓存只保留压缩字节，不长期保留解码器、GPU 上下文或临时路径。

这些准备任务沿用原有后台线程池预算。等待共享结果时每 50ms 检查取消；旧生产者取消后，有效请求可以重新计算。取消、素材失效和超时结果不会成为永久缓存。界面无需等待整个播放区间准备完成才能编辑，预览尺寸、效果参数、编码档位和用户操作流程均不因此改变。

## 连续播放与后台准备

暂停且没有拖动时，编辑器空闲 600ms 后顺序准备后面至多三个两秒窗口；播放时提前准备，不必等当前窗口完成解码。预取与实际播放共用同一个压缩媒体缓存键，不改变画质和渲染内容，也不预取整条长时间线。

后台窗口以较低优先级排队。不同位置的前台定位可以中断正在计算的投机窗口；同一窗口的播放请求继续复用在途结果。完整预览准备只重试被让出的窗口，其父任务不会因此取消。视觉修改后，完整连续预览会在一秒空闲后重建；后续修改或离开工程会取消旧快照，准备完成后自动使用连续文件播放，无需重新打开工程。字幕正文修改仍使用可编辑叠层，不重建基础视频。

这些改动减少等待和重复计算，并让已准备的复杂区间连续播放；首次生成复杂效果仍取决于设备和效果计算量，不承诺任意效果栈均能即时逐帧生成。

## 可重复验证

在仓库根目录运行（Windows）：

```powershell
.venv\Scripts\python.exe -m pytest tests/rendering/test_render_memo.py tests/rendering/test_static_graphic_stacks.py tests/rendering/test_preview_decode_seek.py -q
.venv\Scripts\python.exe tools/verify/benchmark_render_reuse.py .artifacts/render-reuse-run
```

基准输出目录必须是新目录。脚本生成 1280×720、24fps 的透明静态蒙版工程，依次执行四次定位帧、两次半秒预览和两次半秒导出，并在操作之间改变图层位置。输出包括逐项耗时、静态处理子进程数量和所有输出解码像素的 SHA-256；视频统一使用 CPU H.264 编码，以便同机对比。

修改前可另存 `src/cutvoke/rendering/render.py`，然后用 `--renderer-source <保存的路径>` 执行同一工作负载。此入口只适用于与当前依赖兼容的渲染器快照。比较对应输出的像素哈希，并分别观察首次计算与已有缓存的操作；基准总耗时还包括校验用的视频解码，渲染耗时应取 `phases[].seconds`。

实际工程对比使用 `tools/verify/benchmark_project_render.py`：

```powershell
.venv\Scripts\python.exe tools/verify/benchmark_project_render.py project.json .artifacts/before --source-root path/to/frozen/src --mode preview --start 26 --duration 2 --repeat 2
.venv\Scripts\python.exe tools/verify/benchmark_project_render.py project.json .artifacts/after --mode preview --start 26 --duration 2 --repeat 2
```

完整冻结 `src/cutvoke` 包作为基线，并保留其静态资产可访问。脚本支持裸工程或 `{project: ...}` 快照、poster/preview/export；记录源码与工程哈希、阶段耗时、编码器、解码帧数、像素与音频样本哈希。`--cold` 会为每次操作新建服务和临时缓存，`--profile` 保存剖析数据；首次操作和已有缓存后的操作应分开比较。校验解码不计入渲染耗时，失败报告会保留错误信息。

实际工程跑分应保留工程尺寸与全部效果，只限定测量的时间区间。对比不仅检查速度，还须检查像素、音频、旧任务取消、拖动、播放和撤销。缓存及区间导出的收益不能推广为整片首次导出或所有视频效果链的提速倍数；复杂场景仍可能无法实时生成目标帧。
