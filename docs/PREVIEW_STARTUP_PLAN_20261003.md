# 工程打开与立即播放：诊断和改进方案

## 已实现：快速首帧与加载反馈

按用户确认的两项要求，2026-10-03 已完成前端实现并重新构建：

1. 工程打开时并行请求当前播放头的 640×360 合成帧，连续视频尚未解码时先显示该帧。单帧使用现有完整合成接口，字幕继续由编辑器叠层绘制；不会跳过入场动画或把 0.5 秒画面当作第 0 帧。
2. 预览准备时显示旋转指示和明确的等待说明。立即点击播放会显示「准备完成后自动播放」，并提供「取消」；取消后视频即使就绪也保持暂停。
3. 收到原生 `playing` 事件后才显示「播放中」。视频就绪后撤下占位帧与提示；播放中等待后续画面时显示缓冲提示。
4. 按预览区域大小和所选画布比例确定尺寸，避免媒体解码后固有尺寸引起缩放。过期帧请求中止，旧响应不会覆盖新播放头；对象 URL 在替换和卸载时释放。

## 修改前诊断

提出方案时尚未修改产品代码。使用原「潮汐藏馆｜成片剪辑工程」的 SQLite 在线备份副本，在 8821 端口、空预览缓存下复现用户操作；未编辑原工程。浏览器立即播放截图与用户提供的缓冲空画面一致。

- 单帧接口在 0.5 秒处返回一帧：0.387 秒。此数值不代表完整连续播放，也不能直接保证全部多轨效果的占位一致性。
- 第 0 段视频响应开始：1.411 秒；请求完成：1.412 秒。
- 从点击打开工程到 `playing`：1.774 秒；从 `play` 到 `playing`：1.270 秒。
- 同一段生成后，再次 Range 请求：0.106 秒。缓存确实有效。
- 加载截图中的画布比视频就绪后的画布小，说明尺寸还受媒体固有尺寸影响。
- 为只测第 0 段，诊断浏览器拦截了第 1 段的预取。该样本不代表所有工程与长时间播放。

证据：`output/acceptance/preview-startup-20261003/startup-result.json`、`cold-immediate-play.png`、`cold-ready.png`、`cold-frame-result.json`、`measure-browser.js`。

## 修改前原因

1. `Player.tsx` 加载一个完整的 8 秒 `preview-window`。服务端在 `_preview_window_file` 内渲染到临时 MP4，完成后 rename，再返回可播文件；当前不是边生成边播放。
2. 没有首帧占位层。用户立即播放时，视频还没有解码数据，只显示「缓冲中」。
3. `onPlay` 就把状态显示成「播放中」，实际 `playing` 此时尚未发生。
4. 当前段的下一段预取需要 `playing` 状态触发；已有内容缓存与按窗口失效机制需要保留。
5. 渲染持有全局 `_preview_lock`，缓存命中的请求也需要等这把锁。后台预取可能延迟用户当前需要的窗口。

## 原方案与后续任务

| 优先级 | 任务 | 验收要点 |
|---|---|---|
| 已实现 | 优先请求合成首帧，连续视频加载时显示占位帧 | 真工程合成帧、过期响应隔离；持久化首帧缓存尚未实现，可在后续按实际需求增加 |
| 已实现 | 固定预览画布尺寸，改进准备与缓冲状态 | 首帧至视频就绪尺寸一致；准备时点击播放记录意图，就绪自动播放；可取消；底部提示保留画面 |
| P1 | 增加 1–2 秒启动段、合适的预览清晰度和后台预取 | 尽早取得首个可播段；预览清晰度不改变导出质量；首段到后续段无画面跳动、音画不同步、重复或丢帧；不能只缩短所有窗口导致更频繁缓冲 |
| P1 | 调整渲染调度与锁范围 | 当前播放头优先于预取；缓存读取不被无关渲染阻塞；取消过期任务；限制并发与内存；重复请求只生成一份 |
| P2 | 评估 MSE 分片连续追加 | 将新段追加到一个播放缓冲区，减少更换 video 元素的解码等待；与现有 8 秒 MP4 缓存并行验证后再替换 |

用户本次确认的首帧与等待反馈已完成。启动段与调度仍待实现；预取与持久窗口缓存已经存在，不能把现有能力当成新增任务重复实现。

## 原拟定性能目标（尚未全部达到）

缓存命中时尽快呈现画面；首次冷开争取 0.5 秒内显示一致的占位帧，普通工程约 1 秒内开始播放。复杂效果工程按真实测量给出范围；跨段连续播放、拖动、快速切工程、暂停取消、素材失效与导出一致性都须单独验收。
